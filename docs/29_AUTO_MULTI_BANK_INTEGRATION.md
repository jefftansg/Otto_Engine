# Otto Auto + multi-bank SGD — unreleased integration candidate

22 November 2026. PR #21 now combines the local Auto workflow previously developed in PR #19 (`de71953`) with the reviewed multi-bank controls (`001539e`). This is a selective code integration, **not a GitHub merge or a release**. The visible release label and launcher remain **1.3.1**, with an explicit unreleased Auto/multi-bank candidate badge. Lighthouse StudioWorks' internal bookkeeping, MA and draft-UFS service model is unchanged.

## Run and use

Run the current development checkout with `OTTO_PORT=8510 zsh START_ON_MAC.command`; keep its Terminal open and visit localhost:8510. Save an existing workspace ZIP before restarting its own process. An already-open browser session may retain its selected view; select **Workspace view → Auto**. No other running Otto process is stopped automatically.

- Auto is the default for a new session, new company, restored ZIP and fictional example. Guided and Advanced remain explicit sidebar choices and share the same package.
- Auto starts with one **Drop bank statements, bookkeeping records and report references here** uploader. Analysis is local, bounded and advisory; no cloud/on-device LLM or OCR is connected. Optional external AI JSON proposals are source/revision validated and require human category approval; Otto does not send them to a provider.
- A blank, unposted workspace with identifiable bank sources presents **Review identified bank accounts**. This creates an empty registry only, then keeps the user in Auto for per-account source, coverage and transaction review. Neither analysis nor this navigation action posts a transaction, approves coverage or invents an opening counterpart.
- Multi-bank ZIPs open directly inside Auto. The shared upload inventory feeds the existing **Approve account identity and coverage**, transaction-staging and **Approve this transfer pair** controls. Existing single-account books retain their import/editor path; automatic migration of a populated single-account ledger remains blocked.
- Company identity, entity type, proposed framework and reporting dates require contextual confirmation. Existing books cannot silently change UEN. Source/date changes make managed account reviews stale and reset source/transaction confirmation controls to the current revision. Wider eligibility/disclosure decisions remain human responsibilities.
- Auto shows suggested transfers, categories with bank/reference identity, independent reconciliations and a persistent exception inbox. **Detailed bank registry, opening journals and other accounting records** opens the same source-preserving editors. Guided/Advanced multi-bank views deliberately use those account-aware editors, never the single-account tables.
- Category approval cannot overwrite either leg of a reviewed transfer. Category/AI/undo revisions bind bank control, transfer link and source row identity as well as financial fields. Legacy one-account import APIs reject a multi-bank workspace.
- Multi-bank report generation is blocked by ledger/source errors in the UI and export API. Frozen provisional bundles contain MA, company UFS, Excel, inventory, exceptions and a report manifest; snapshot/layout/renderer/file hashes identify the exact frozen result. No output is authorised automatically. The same provisional snapshot rules apply when an Auto workspace is exported through detailed views.
- ZIP restoration adds empty optional CSV cells; snapshot hashing treats those as semantically empty, avoiding false report revisions. Review/source metadata and transfer/category history survive restore. New-company/restore/demo actions clear staged AI proposals and frozen bundles; uploader keys separate client sessions.
- Existing multi-bank workspaces keep the classic layout by default. Optional reference typography profiles from the Auto preview remain provisional and selectable. A missing original or unapproved source never becomes verified merely because a saved ledger reconciles.

## Engineering verification

Full command: `PYTHONDONTWRITEBYTECODE=1 python -m unittest discover -s tests -v`, using the existing pinned M0 environment on macOS arm64/Python 3.9.6. **171 tests passed, no skips**: the prior 140 cases, 21 Auto/OCBC cases ported from PR #19 and ten new combined-flow cases. `pip check` and `git diff --check` passed. GitHub's three-platform matrix is separate live evidence on PR #21.

New `tests/test_auto_multi.py` verifies new-source account review without posting, restored multi-bank Auto entry, Auto/detailed-view ledger equality, transfer/category protection, source-bound revisions, blocked legacy import, current-source readiness, stale errors blocking bundle export, frozen report/ZIP equality and new-client cache clearing. Existing Guided/Advanced tests now explicitly select their view so they continue testing the retained interfaces while Auto becomes the default. The original multi-bank reconciliation tests remain unchanged.

The independent acceptance ledger remains: bank A opening 1,000, receipt 500, internal transfer 300, closing 1,200; bank B opening 500, transfer receipt 300, expense 200, closing 600. Consolidated opening 1,500, operating cash/profit 300, closing 1,800, investing/financing zero. Frozen bundle workbooks retain numeric balances, per-bank reconciliation, statement sources and reviewer-linked transfer workpapers.

Renderer verification compared the legacy sample to `001539e`: PDF character text/font/size/position and Excel sheet/cell/formula equality pass for unselected classic layouts. All three selectable profiles rendered the combined synthetic snapshot: **14 MA landscape + 5 UFS portrait pages each, 57 pages total**, inspected as a contact sheet; character bounds were checked on every page and each workbook's closing cash remained 1,800 without error cells. These reference profiles are not approved master templates. Browser smoke inspection on the isolated local server confirmed Auto selected by default, the combined-candidate label, upload-first screen, available view selector and no required initial company form. Synthetic AppTest, rather than a real financial attestation, exercises review/posting actions. Existing running servers may retain their prior displayed upload-size configuration until restarted; processing limits are enforced by the parsers.
